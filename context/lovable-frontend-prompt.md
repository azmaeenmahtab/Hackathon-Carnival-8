# Lovable Frontend Prompt — Faculty Email Intelligence Dashboard

Copy everything below into Lovable as your build prompt.

---

Build a React web app called **"FacultyInbox AI"** — an intelligent email triage dashboard for university faculty. This is a frontend-only build for now; use realistic mock/sample data (no real backend calls yet, but structure the data and components so an API can be wired in later).

## Overall Purpose

Faculty members receive a high volume of email across meetings, classes, student issues, exams, and re-evaluation requests. This app ingests an inbox, and each email THREAD has already been analyzed by AI to receive: a category, an urgency level, a short "why this matters" explanation, an action-needed flag, and an optional deadline. The app's job is to present this triaged inbox clearly — prioritizing what matters, and flagging threads that have gone unanswered.

Design tone: clean, calm, professional academic tool — not flashy. Think "a well-designed internal university tool," not a consumer app. Faculty using this may not be highly tech-savvy, so clarity beats cleverness.

## Data Model to Use for Mock Data

Model everything around **email THREADS**, not individual messages (a thread = one conversation, may have 1-6 messages).

```
Thread {
  id: string
  subject: string
  participants: string[] // names/emails
  lastMessagePreview: string
  lastMessageAt: datetime
  messageCount: number
  messages: [
    { sender: string, isFaculty: boolean, sentAt: datetime, body: string }
  ]
  category: "Meeting" | "Class/Schedule" | "Student Issue" | "Examination" |
            "Re-evaluation" | "Committee/Admin" | "Other"
  urgency: "Low" | "Medium" | "High" | "Critical"
  actionNeeded: boolean
  deadline: date | null
  aiExplanation: string // one-line reasoning, e.g. "Student disputes grade and requests re-evaluation before Friday deadline"
  isRead: boolean
  needsFollowUp: boolean // computed: faculty not last sender + unread/unanswered + past age threshold
  correctedCategory: string | null // if faculty manually reclassified
}
```

Generate **20-25 realistic mock threads** spanning all 7 categories, with varied urgency, some read/unread, some with `needsFollowUp: true`, a couple of genuinely ambiguous ones correctly landing in "Other" (e.g. a university newsletter, an IT security notice, a conference invitation) — these should have urgency defaulted to Low and `needsFollowUp: false` regardless.

## Screens / Components

### 1. Top-Level Layout
- Left sidebar (or top nav on mobile): app name/logo, nav links — **Dashboard**, **All Threads**, **Needs Follow-Up**, **Other/Low Priority** (visually de-emphasized, e.g. grayed icon or muted color).
- Simple faculty user badge top-right (name + avatar placeholder) — no real auth needed, just static.

### 2. Dashboard (main/home view)
This is the primary screen judges will see. Top to bottom:

- **AI Daily Digest card** — a prominent card at the top, styled distinctly (subtle accent border/background), containing a 3-5 sentence AI-generated plain-English summary of the top priority items right now (e.g. "You have 2 critical items: a re-evaluation request from a student due tomorrow, and an unanswered department meeting invite from 3 days ago. Your exam committee thread also needs your input before Thursday."). Include a small "Generated by AI" or sparkle icon label so it's clearly an AI feature, not static text.
- **Priority stat strip** — small stat cards/pills: count of Critical, count of High, count needing follow-up, count unread. Use color coding (red/orange/yellow/gray or similar) consistently across the whole app for urgency.
- **Category tabs or filter chips** — Meeting, Class/Schedule, Student Issue, Examination, Re-evaluation, Committee/Admin, Other. Clicking filters the thread list below. "Other" tab should look visually muted/secondary compared to the rest.
- **Thread list** (sorted by urgency first, then recency) — each thread row/card shows:
  - Subject line
  - Sender/participants
  - Category badge (color or icon per category)
  - Urgency badge (color-coded: Critical=red, High=orange, Medium=yellow, Low=gray)
  - One-line AI explanation (this should be visually prominent — it's the core "AI reasoning" feature, not buried as metadata)
  - Deadline chip if present (e.g. "Due: Fri, Sep 12")
  - Unread indicator (bold/dot)
  - "Needs Follow-Up" flag/ribbon if applicable
  - Relative timestamp ("2 days ago")

### 3. Thread Detail View
Clicking a thread opens a detail panel/page showing:
- Full subject + category + urgency badges at top
- The AI explanation, restated clearly (e.g. in a highlighted callout box)
- Full message history in the thread, chat-style or email-style (sender, timestamp, body), oldest to newest
- A visible "Needs Follow-Up" banner if applicable, explaining briefly why (e.g. "Unread for 3 days — appears to expect a reply")
- A **reclassify control** — small dropdown/menu letting faculty manually change the category (this stores `correctedCategory` and should visually confirm the change, e.g. a toast "Reclassified to Committee/Admin")
- Mark as read/unread toggle (mock only, just updates local state)

### 4. Needs Follow-Up View
A filtered list showing only threads where `needsFollowUp: true`, sorted by how long they've been waiting. Each row should clearly show "waiting X days" and why it was flagged. This screen should feel like the "don't let this slip through the cracks" safety net — give it a slightly more urgent visual tone (but not alarming/red-everywhere; tasteful).

### 5. Other/Low Priority View
A quieter, collapsed-by-default list of "Other" category threads — framed as "filtered out of your priority view" rather than hidden/deleted. Maybe include a small stat like "X emails automatically filtered as non-academic this week" to reinforce the value of the filtering.

### 6. Empty / Loading States
Since this will later connect to a real backend, build proper:
- Loading skeleton states for the thread list and digest card
- Empty state for "Needs Follow-Up" when there's nothing pending (positive framing: "You're all caught up 🎉" or similar, understated)
- A subtle error/retry state pattern (can be a static component even if unused in mock mode)

## Visual/Style Guidelines
- Consistent color coding for urgency across every screen (same red/orange/yellow/gray everywhere).
- Distinct, muted iconography or color-coding per category so users learn to scan visually rather than read every label.
- Prioritize information density that's still readable — this is a working tool used daily, not a marketing page.
- Responsive layout (usable on a laptop primarily, but shouldn't break on tablet width).
- Keep the "AI explanation" line visually distinct (e.g. italic, subtle icon, or tinted background) everywhere it appears, so it reads as "the AI's reasoning," separate from raw email metadata.

## Interactivity Expected (mock-data level, no backend needed yet)
- Filtering by category and urgency
- Opening thread detail
- Reclassifying a thread (updates local state + visual confirmation)
- Marking read/unread
- Everything should work smoothly against the mock dataset defined above — structure state/data fetching so swapping mock data for real API calls later is straightforward (e.g. keep a single data-fetching layer/hook rather than scattering mock data across components).

Build this as a clean, componentized React app ready to hand off and later port to Next.js.
